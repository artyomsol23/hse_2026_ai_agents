# Design

## Context

См. `proposal.md` — Why. Изменение создаёт приложение с нуля, поэтому ограничения задают архитектуру: только файлы `index.html`, `styles.css`, `app.mjs`, `domain.mjs`, `tests/acceptance.test.mjs`; без CDN, внешних библиотек и API-ключей; расчёты должны проверяться автоматически через `node:test`. Требования к поведению — в `specs/tracker/spec.md`.

## Goals / Non-Goals

**Goals:**
- Отделить чистую логику (расчёты, валидация) от работы с DOM, чтобы её можно было тестировать в Node без браузера.
- Обеспечить детерминированный стартовый набор данных и предсказуемые метрики.
- Оставить приложение полностью автономным и офлайновым.

**Non-Goals:**
- Не проверять DOM, вёрстку и ширину 390 px автоматически — это ручные проверки.
- Не вводить сборщик, транспиляцию, фреймворки и сервер.
- Не реализовывать серверную часть, синхронизацию и аккаунты.

## Decisions

- **Разделение `domain.mjs` и `app.mjs`.** `domain.mjs` содержит чистые функции: создание/валидацию задачи, добавление, удаление, переключение `done`, расчёт суммы часов и прогресса, фильтрацию. `app.mjs` связывает их с DOM и событиями. Альтернатива — единый `app.mjs`: отклонена, потому что тогда расчёты нельзя импортировать в `node:test` без браузерного окружения.
- **ES-модули (`.mjs`).** Нативный `<script type="module">` и `import` в тестах без сборки. Альтернатива — глобальные скрипты: отклонена из-за невозможности импорта в тестах.
- **Данные в памяти как источник истины.** Состояние — массив задач; DOM перерисовывается из состояния при каждом изменении (простая функция рендера). Альтернатива — мутировать DOM напрямую: отклонена из-за рассинхронизации метрик и списка.
- **Прогресс как чистая функция с защитой от нуля.** Возвращает 0 при пустом наборе; округление выполняется один раз над итоговым процентом.
- **Метрики считаются по полному набору.** Функции расчёта принимают все задачи; фильтр применяется только к копии списка для рендера.
- **Валидация возвращает результат, а не бросает исключение.** Функция возвращает ошибки по полям, чтобы интерфейс показал сообщение рядом с полем и сохранил введённые значения.
- **`localStorage` как опциональный слой.** Обёртка с `try/catch`; при недоступности — сообщение и продолжение в памяти. Альтернатива — жёсткая зависимость от хранилища: отклонена, приложение должно работать и без него.
- **Тесты через `node:test` + `node:assert`.** Покрывают 25%/75%, независимость метрик от фильтра, валидацию и пустое состояние.

## Risks / Trade-offs

- [Ручные проверки (форма, кнопки, текст ошибок, 390 px) не автоматизированы] → зафиксировать их в `tasks.md` и отметить в отчёте; непроведённые проверки помечать NOT RUN.
- [`localStorage` может быть недоступен или отдавать повреждённые данные] → обёртка с `try/catch` и проверкой структуры; при сбое — откат к набору в памяти.
- [Округление прогресса может давать неожиданные значения на границах] → округлять только итоговый процент и покрыть границы тестами.
- [Рассинхронизация DOM и состояния при прямых манипуляциях] → единственный путь изменения — через состояние и полный перерендер.
